# 해야 할 일

[index.md](index.md)의 순서대로 위에서 아래로 진행한다. 각 단계에서 정해야 할 내용을 해당 기능 문서에 먼저 적는다. 그 내용이 정해지기 전에는 그 기능을 만들지 않는다.

이미 정한 기술과 서버 구분은 [platforms.md](platforms.md)에 있다.

기능별 입력과 데이터 흐름은 이 문서에 다시 적지 않는다. 그 기능을 작업할 때는 그 기능 문서만 보고 고친다.

**A부터 D까지 정하기 전에는 화면을 만들지 않는다.** 아직 정하지 않은 규칙이 화면에 먼저 들어가면, 나중에 설계를 다시 바꿔야 한다.

O까지 진행한 뒤 실제 동작을 확인한다. P부터 R은 스토어에 내고 운영하는 단계다. S의 원칙은 처음부터 끝까지 지킨다.

## A. 제품이 무엇인지 결정하기

[center.md](center.md)에 이미 다음을 정했다.

- 앱 이름은 hoohaa다. 웹과 앱을 다른 이름으로 나누지 않는다.
- 웹 주소는 hoohaa.run이다. 앱은 스토어 앱이라 따로 쓸 웹 주소는 없다. 폰이 접속하는 서버 주소는 E에서 정한다.
- 새 앱은 hoohaa.run을 폰으로 넓힌 제품이다.
- 기존 웹 화면을 그대로 폰으로 옮기는 것은 아니다.
- 티어와 VDOT 계산 기준은 기존 hoohaa.run과 같다.
- 계정과 운동 기록은 하나다. 웹과 앱이 각자 복사해 갖지 않는다.
- 지금 웹앱에는 로그인을 넣지 않는다.
- 누구를 위한 앱인지는 SNS에 기록과 사진을 올리는 젊은 러너다.

한 줄 소개는 아직 제안이다. "러너의 실력을 티어로 보여주고, 기록은 예쁜 사진으로 공유하고, AI가 오늘과 내일의 훈련을 골라 줘요." 들어갈 내용은 실력, 공유용 사진, AI의 훈련 판단이다.

아직 정할 내용:

- 한 줄 소개의 최종 문장

## C. 판단에 쓰기 전에 정할 것

이미 정한 규칙. 컨디션, 목표, 내일 훈련, 러너 유형은 서로의 결과를 받지 않는다. 같은 운동 기록을 각각 따로 판단한다. [engine.md](engine.md), [features/tomorrow.md](features/tomorrow.md)

아직 정할 내용:

- 오늘의 컨디션에 쓸 값이 운동 기록의 어떤 항목인지. [features/condition.md](features/condition.md)
- 최근 운동 기록을 며칠까지 쓸지. 예를 들면 최근 7일 또는 최근 14일
- Jev에 어떤 언어로 넣을지. 화면에 보이는 문장은 한국어 해요체다. [engine.md](engine.md), [features/copy.md](features/copy.md)
- 텍스트 판단에 쓸 모델을 `jev-1.13.0`으로 고정할지. 아직 제안이다. 정하면 [engine.md](engine.md)에 결정으로 적는다
- 운동이 끝난 뒤의 여러 판단을 Jev 호출 한 번으로 처리할지. 아직 제안이다
- 목표 달성을 choice로 물을지 score로 물을지. [features/goal.md](features/goal.md)
- 러너 유형의 전체 목록, 각 유형을 가르는 기록의 정의, 칭호를 주기 전에 필요한 기록 수. [features/runner-type.md](features/runner-type.md)
- 내일 훈련에서 강한 메뉴가 무엇인지. [features/tomorrow.md](features/tomorrow.md)

## D. 문장

[features/copy.md](features/copy.md)의 빈 표를 채운다. 판단 결과에 쓸 문장을 정하기 전에는 판단 화면을 만들지 않는다.

정할 문장:

- 그대로 훈련
- 강도 낮추기
- 휴식
- 판단 보류
- 달성 유력
- 가능
- 어려움
- 내일 훈련 메뉴. E·M·T·I·R에 맞춘다. 페이스 숫자는 코드가 계산해서 문장에 넣는다
- 달리는 중: 유지, 낮추기, 올려도 됨
- 러너 유형 칭호가 없을 때 보여줄 문장

컨디션 문장 옆에 의료 조언이 아니라는 안내를 넣을지도 여기서 정한다. 아직 제안이다.

## E. 집 서버

개발과 검증에서는 집의 서피스 프로(Windows)를 서버로 쓴다.

서버가 하는 일:

- TypeScript로 만든 HTTP API
- 회원 계정
- 운동 기록 저장과 조회
- Jev 호출

`TYPESAFE_API_KEY`는 서피스 프로에만 둔다. 폰 앱과 소스 저장소에는 넣지 않는다.

폰이 호출하는 API의 요청과 응답 형식은 개발 서버와 운영 서버가 같다. 운영으로 옮길 때는 서버 장비만 바꾸고, API 형식은 바꾸지 않는다. [platforms.md](platforms.md)

아직 정할 내용:

- 집 밖에서 폰이 접속할 HTTPS 주소

개발 서버라서 다음이면 접속이 끊길 수 있다. 이것은 개발·검증의 한계로 둔다.

- 서피스가 절전에 들어간 경우
- 덮개를 닫은 경우
- 재부팅된 경우
- 집 IP가 바뀐 경우
- 집 네트워크가 끊긴 경우

## F. 폰 앱

- React Native와 TypeScript로 iPhone과 Android를 하나의 코드로 만든다.
- Expo Go는 쓰지 않는다. 건강 데이터 권한이 필요하므로 개발 빌드(prebuild)를 쓴다.
- 기존 웹의 화면은 고치지 않는다. 웹앱은 `9171085`에서 개발을 끝낸 상태로 둔다.
- 웹의 사진 편집기를 폰으로 옮기는 일은 이 단계에서 하지 않는다.

## G. 계산 연결

- 티어와 VDOT 계산 코드는 하나만 둔다. 웹용과 앱용으로 복사하지 않는다. [features/tier-vdot.md](features/tier-vdot.md)
- 그 코드를 어디에 두고 웹과 앱이 어떻게 가져다 쓸지는 아직 정하지 않았다. 공통 패키지로 만들 수도 있고, 앱이 지금의 `src/engine`을 직접 쓸 수도 있다. [features/tier-vdot.md](features/tier-vdot.md)에서 정한다.
- 티어 구간과 VDOT 공식은 바꾸지 않는다.

## H. 로그인과 기록

B와 E를 정한 뒤에 만든다. 화면보다 운동 기록의 데이터 구조를 먼저 정한다.

사용자 계정 아래에 운동 기록이 여러 개 있다. 각 기록에는 다음이 들어간다.

- 어디서 가져온 기록인지
- 측정된 운동 데이터
- 사용자가 직접 넣은 데이터
- 운동 경로

컨디션, 목표, 내일 훈련, 러너 유형의 판단 결과도 그 운동 기록에 연결한다. 각 결과에 넣을 세부 항목 이름은 그 기능을 정의할 때 해당 문서에 적는다.

만드는 것:

- 회원 로그인
- 공유로 받은 운동 기록 저장
- 사용자가 직접 넣은 운동 기록 저장
- 날짜, 거리, 시간, 평균 심박, 체감 피로 1~10, 수면 시간, 메모

## I. 오늘의 컨디션

C와 D를 정하고, H의 기록 구조를 만든 뒤에 만든다. [features/condition.md](features/condition.md)

- 앱이 판단에 필요한 상태 JSON을 만든다.
- Jev에 정해 둔 choice를 묻는다.
- 세 가지 확률과, 그 결과에 맞춰 미리 써 둔 문장을 보여 준다.
- 판단 신뢰도가 기준보다 낮으면 앱이 판단 보류로 처리한다.
- 그 기준 숫자는 N에서 정하기 전에는 정하지 않는다.

## J. 목표 달성

다음을 정한 뒤에 만든다.

- 목표 대회와 목표 기록을 어떤 항목으로 받을지
- 최근 훈련량을 어느 기간으로 계산할지
- VDOT는 코드가 계산해서 판단에 넘긴다
- 달성 가능성은 확률로 보여 주고, 훈련 메뉴에서 고른 제안 1~2개를 함께 보여 준다

## K. 내일 훈련

- 메뉴 문장은 D에서 정한다.
- 컨디션 판단 결과를 내일 훈련의 입력으로 쓰지 않는다. 내일 훈련도 같은 운동 기록을 따로 본다. 이것은 이미 정했다.
- 컨디션과 내일 훈련의 결과가 서로 안 맞을 때, 화면에서 휴식 쪽으로 바꿀지는 아직 정하지 않았다. 그 규칙을 정하기 전에는 그 동작을 만들지 않는다.

## L. 러너 유형

- 유형 목록과 판단 기준을 먼저 정한다. 정하기 전에는 러너 유형 카드를 만들지 않는다.
- 판단 신뢰도가 낮거나 기록이 적으면 칭호를 주지 않을지는 아직 제안이다. 그 규칙을 정한 뒤에 만든다.

## O. 개발 검증

여기까지 만든 뒤 집 서버와 개발용 폰에서 동작을 확인한다. 스토어에는 올리지 않는다. P부터는 스토어 출시와 운영이다.

확인할 내용:

- 운동 기록이 저장된다
- 컨디션, 목표 달성, 내일 훈련, 러너 유형이 확률과 정해 둔 문장으로 나온다
- Jev API 키가 폰에 들어 있지 않다
- 서피스가 절전에 들어가면 서버에 연결되지 않는다는 것이 사용자에게 보인다

## P. 스토어

O를 마친 뒤에 시작한다. 그 전에는 개발자 계정과 앱 패키지 이름을 정하지 않는다.

- Apple 개발자 계정, 인증서, HealthKit 권한
- iPhone 빌드. Xcode가 있는 Mac에서 만든다. 그 Mac은 클라우드 빌드일 수 있다
- Google Play 계정, Android 빌드
- 개인정보 처리방침과 스토어 설명. 웹의 처리방침을 그대로 복사하지 않는다. 계정과 건강 데이터를 다루는 내용을 따로 적는다

## Q. 운영 서버

P 다음에 시작한다. 스토어에 나가는 앱은 집의 서피스 프로를 서버로 쓰지 않는다. 업체는 실제 트래픽과 비용을 확인한 뒤에 정한다. E에서 정한 API 형식은 그대로 둔다.

개발 서버와 다른 것:

- 서버 장비
- Jev API 키
- 운동 기록을 저장하는 위치

운영용 키는 서피스의 개발용 키와 따로 둔다.

## R. 워치

폰 앱과 운영 서버가 된 뒤에 한다. [features/live-pace.md](features/live-pace.md)는 나중 기능이다.

- 애플워치는 SwiftUI, 웨어 OS는 Kotlin. 앱은 둘이다
- 워치에서 Jev를 직접 호출하지 않는다
- 첫 화면을 오늘의 판단으로 할지, 달리는 중 페이스로 할지
- 운동 데이터를 얼마나 자주 받을지
- 심박을 어디에서 받을지
- 화면이 잠겼을 때 무엇을 보여줄지
- 폰과 통신이 끊기면 무엇을 보여줄지

## S. 하지 않는 일

다음 원칙은 처음부터 끝까지 지킨다.

- 웹앱에 새 기능을 넣지 않는다
- 웹앱을 웹뷰로 감싸 스토어에 내지 않는다
- 웹앱을 React로 다시 만들지 않는다
- 티어와 VDOT를 Jev에게 계산시키지 않는다
- Jev에게 사용자에게 보여줄 문장을 쓰게 하지 않는다
- [parked.md](parked.md)의 후보는 만들지 않는다. 캡처 인증, 얼굴 위치 배치, 사진 품질 점수, 테이퍼, 부상 판단, 시즌 배지
- 판단 보류를 Jev의 선택지로 보내지 않는다
- 운동 기록을 사람이 임의로 요약해서 Jev에 넘기지 않는다. Jev에 넘기는 파생 값은 코드에 적어 둔 규칙으로 계산한 것만 쓴다
- 한 판단의 결과를 다른 판단의 입력으로 쓰지 않는다
