# 해야 할 일

[index.md](index.md)의 순서대로 위에서 아래로 진행한다. 각 단계에서 정해야 할 내용을 해당 기능 문서에 먼저 적는다. 그 내용이 정해지기 전에는 그 기능을 만들지 않는다.

이미 정한 기술과 서버 구분은 [platforms.md](platforms.md)에 있다. 다음에 볼 범위는 [next.md](next.md)에 있다.

기능별 입력과 데이터 흐름은 이 문서에 다시 적지 않는다. 그 기능을 작업할 때는 그 기능 문서만 보고 고친다.

**A부터 D까지 정하기 전에는 화면을 만들지 않는다.** 아직 정하지 않은 규칙이 화면에 먼저 들어가면, 나중에 설계를 다시 바꿔야 한다.

O까지 진행한 뒤 실제 동작을 확인한다. P부터 R은 스토어에 내고 운영하는 단계다. S의 원칙은 처음부터 끝까지 지킨다.

## A. 제품이 무엇인지 결정하기

[center.md](center.md)에 이미 다음을 정했다.

- 앱 이름은 hoohaa다. 웹과 앱을 다른 이름으로 나누지 않는다.
- 웹 주소는 hoohaa.run이다. 앱은 스토어 앱이라 따로 쓸 웹 주소는 없다. 앱은 hoohaa.run을 호출하지 않고 `<개발용 API 주소>`를 호출한다. 그 이름은 아직 정하지 않는다.
- 새 앱은 hoohaa.run을 폰으로 넓힌 제품이다.
- 기존 웹 화면을 그대로 폰으로 옮기는 것은 아니다.
- 티어와 VDOT 계산 기준은 기존 hoohaa.run과 같다.
- 계정과 운동 기록은 하나다. 웹과 앱이 각자 복사해 갖지 않는다.
- 지금 웹앱에는 로그인을 넣지 않는다.
- 누구를 위한 앱인지는 SNS에 기록과 사진을 올리는 젊은 러너다.

**결정.** 한 줄 소개는 "러닝 기록을 티어와 예쁜 카드로 남기고, AI가 다음 훈련까지 안내해 줘요."다. [center.md](center.md)

## B. 건강 데이터가 들어오는 길

[features/health-import.md](features/health-import.md)에 이미 정한 것. 건강 앱에 쌓인 기록을 폰이 자동으로 읽는다. 그 운동에 들어 있는 항목은 빠짐없이 가져온다. 사진, GPX, FIT를 사용자가 올리지 않는다. 그래서 새 앱은 폰 앱이다. 아이폰은 애플 건강, 안드로이드는 헬스 커넥트다. 같은 운동을 두 번 저장하지 않는다.

체감 피로 1~10은 사용자에게 한 번 묻는다. 같은 자리에서 메모를 쓸 수 있고, 필수는 아니다. 예시는 어디가 아픈지다. 건강 앱 기록과 이 값은 JSON으로 넘기고, Jev는 정해 둔 보기 안에서만 고른다.

건강 데이터 권한은 C와 D를 정한 뒤에 만든다. 경로를 화면에 넣는 방식은 M, 기록을 둘 서버는 E에서 정한다. 항목 이름과 같은 운동으로 보는 기준은 그때 코드에 적는다.

## C. 판단에 쓰기 전에 정할 것

이미 정한 규칙. 컨디션, 목표, 내일 훈련은 서로의 결과를 받지 않는다. 같은 운동 기록을 각각 따로 판단한다. 최근 기록은 14일을 본다. 오늘의 컨디션에는 그 14일 기록과 체감 피로, 메모를 JSON으로 넣는다. Jev에 보내는 글은 영어다. 화면 문장은 한국어다. 운동이 끝난 뒤의 세 판단은 Jev 호출 한 번으로 묻는다. 러너 유형은 그 호출에 넣지 않고, 기록 카드의 뱃지로 코드가 본다. [engine.md](engine.md), [features/condition.md](features/condition.md), [features/tomorrow.md](features/tomorrow.md), [features/runner-type.md](features/runner-type.md)

아직 정할 내용:
- 텍스트 판단에 쓸 모델을 `jev-1.13.0`으로 고정할지. 아직 제안이다. [engine.md](engine.md)

## D. 문장

[features/copy.md](features/copy.md)에 종류별로 정했다. 운동이 끝난 뒤 화면은 컨디션, 목표, 내일 훈련이다. 유지, 낮추기, 올려도 됨은 실시간 안내이고 그 화면에서 쓰지 않는다.

컨디션 문장 옆에 "의학적인 진단은 아니에요."를 둔다.

## E. 집 서버

개발과 검증에서는 집의 서피스 프로(Windows)를 서버로 쓴다.

서버가 하는 일:

- TypeScript로 만든 HTTP API
- 회원 계정
- 운동 기록 저장과 조회
- Jev 호출

`TYPESAFE_API_KEY`는 서피스 프로에만 둔다. 폰 앱과 소스 저장소에는 넣지 않는다.

**결정.** 앱은 hoohaa.run 웹을 호출하지 않는다. 계정, 운동 기록, Jev 호출은 별도의 API를 통해 처리한다. 개발 중에는 이 API를 집 서피스 프로에서 운영하며, HTTPS 개발용 주소를 별도로 사용한다. 운영 전환 시 API 서버만 교체하고 앱의 API 호출 형식은 유지한다. 개발용 API 주소의 이름은 아직 정하지 않는다. 문서에서는 `<개발용 API 주소>`로만 적는다. [platforms.md](platforms.md)

개발 서버라서 다음이면 접속이 끊길 수 있다. 이것은 개발·검증의 한계로 둔다.

- 서피스가 절전에 들어간 경우
- 덮개를 닫은 경우
- 재부팅된 경우
- 집 IP가 바뀐 경우
- 집 네트워크가 끊긴 경우

## F. 폰 앱

- React Native와 TypeScript로 iPhone과 Android를 하나의 코드로 만든다.
- Expo Go는 쓰지 않는다. 건강 데이터 권한이 필요하므로 개발 빌드(prebuild)를 쓴다.
- 기존 웹의 화면은 고치지 않는다. 웹앱은 `9171085`에서 개발을 끝낸 상태로 둔다.
- 웹의 사진 편집기를 폰으로 옮기는 일은 이 단계에서 하지 않는다.

## G. 계산 연결

- 티어와 VDOT 계산 코드는 하나만 둔다. 웹용과 앱용으로 복사하지 않는다. [features/tier-vdot.md](features/tier-vdot.md)
- 계산 코드는 `src/engine/tier.js`와 `src/engine/data.js`에 둔다. 앱이 그 파일을 직접 가져다 쓴다. 공통 패키지로 옮기지 않는다. 웹의 import 경로는 그대로 둔다. [features/tier-vdot.md](features/tier-vdot.md)
- 티어 구간과 VDOT 공식은 바꾸지 않는다.

## H. 로그인과 기록

B와 E를 정한 뒤에 만든다. 화면보다 운동 기록의 데이터 구조를 먼저 정한다.

사용자 계정 아래에 운동 기록이 여러 개 있다. 각 기록에는 다음이 들어간다.

- 어디서 가져온 기록인지
- 측정된 운동 데이터
- 사용자가 직접 넣은 데이터
- 운동 경로

컨디션, 목표, 내일 훈련의 판단 결과와, 러너 유형에서 성립한 뱃지를 그 운동 기록에 연결한다. 각 결과에 넣을 세부 항목 이름은 그 기능을 정의할 때 해당 문서에 적는다.

만드는 것:

- 회원 로그인
- 공유로 받은 운동 기록 저장
- 사용자가 직접 넣은 운동 기록 저장
- 날짜, 거리, 시간, 평균 심박, 체감 피로 1~10, 수면 시간, 메모

## I. 오늘의 컨디션

C와 D를 정하고, H의 기록 구조를 만든 뒤에 만든다. [features/condition.md](features/condition.md)

- 앱이 판단에 필요한 상태 JSON을 만든다.
- 기준 숫자가 정해져 있고 기록이 충분하면 Jev에 정해 둔 choice를 묻는다.
- 세 가지 확률과, 그 결과에 맞춰 미리 써 둔 문장을 보여 준다.
- 판단 보류는 충분한 기록이 쌓이지 않은 경우에 쓴다. 문장은 "오늘은 판단하지 않아요."다.
- 구체적인 기준 숫자는 실제 기록을 확인한 뒤 정한다. 기준이 정해지기 전에는 컨디션 판단을 하지 않고 이력만 남긴다.

## J. 목표 달성

[features/goal.md](features/goal.md)에 정했다. 목표가 있나요에서 목표 없음과 대회 목표만 받는다. 대회 목표는 대회 이름, 대회 날짜, 목표 종목, 목표 기록이다. 최근 훈련량 기간은 사용자에게 묻지 않고, 숫자는 별도로 정한다.

- VDOT는 코드가 계산해서 판단에 넘긴다
- 달성 가능성은 확률로 보여 주고, 훈련 메뉴에서 고른 제안 1~2개를 함께 보여 준다
- 목표 문장은 대회 목표가 설정된 경우에만 보여 준다

## K. 내일 훈련

- 메뉴 문장은 D에서 정했다. [features/copy.md](features/copy.md)
- 컨디션 판단 결과를 내일 훈련의 입력으로 쓰지 않는다. 내일 훈련도 같은 운동 기록을 따로 본다. 이것은 이미 정했다.
- 강한 메뉴는 T, I, R이다. 가벼운 메뉴는 E다. M은 강한 메뉴가 아니다.
- 컨디션이 휴식이거나 강도 낮추기이고 내일 메뉴를 보여 주면, 컨디션 문장을 앞에 두고 내일 메뉴는 뒤에 둔다. 메뉴를 다른 것으로 바꾸지 않는다. 저장 값은 받은 그대로다.
- 컨디션이 그대로 훈련이거나 컨디션 판단을 할 수 없으면 내일 메뉴를 그대로 둔다. 내일 메뉴만 보류이면 그 메뉴는 보여 주지 않는다.

## L. 러너 유형

[features/runner-type.md](features/runner-type.md)에 정했다. 기록 카드에 붙는 작은 뱃지다. 코드가 조건을 보고, 성립한 것 중 대표만 올린다. 없으면 자리는 비운다.

아래를 정하기 전에는 만들지 않는다.

- 뱃지 이름
- 1차로 둘 뱃지
- 조건의 숫자
- 카드에 몇 개까지 올릴지
- 어떤 것을 대표로 볼지

## M. 사진과 경로

[features/photo.md](features/photo.md)에서 정한다. Jev에는 사진을 보내지 않는다.

편집은 웹과 같이 한다. 템플릿, 사진, 스티커, 기록, 저장과 공유다. 로그인 없이 기기 안에서 한다. 스티커 `data_course`는 거리와 코스 이름을 적어 붙이는 장식 선이다. 뛴 경로가 아니다.

정할 내용:

- 뛴 경로는 카드 맨 아래에 둔다. 다른 스티커처럼 사용자가 옮길 수 있다. 경로가 없으면 올리지 않는다. 웹에는 아직 없다.
- 기존 웹 사진 편집기를 폰 앱으로 옮길지. 첫 폰 버전에는 넣지 않는다.

## N. 판단 이력과 보류 기준

[withhold.md](withhold.md)에서 정한다. 숫자로 된 기준이 없으면 판단 보류 규칙을 만들지 않는다. 컨디션은 예외다. 기준 숫자가 생기기 전에는 판단을 하지 않고 이력만 남긴다. [features/condition.md](features/condition.md)

보여 준 판단은 그때부터 저장한다. 컨디션 판단과 내일 훈련 메뉴를 그 운동 기록에 남긴다. 다음 운동을 기록할 때 "어제 추천한 훈련을 했나요?"를 묻고, 했어요, 바꿨어요, 쉬었어요 중에서 고른다. 실제 운동은 그 기록에서 연결한다. 판단이 맞았는지는 따로 묻지 않는다. [withhold.md](withhold.md)

정할 내용:

- 기능마다 보류 기준을 어떻게 다르게 둘지
- 모델 버전을 바꿀 때 이전 모델과 새 모델의 결과를 어떻게 비교할지. [engine.md](engine.md)

## O. 개발 검증

여기까지 만든 뒤 집 서버와 개발용 폰에서 동작을 확인한다. 스토어에는 올리지 않는다. P부터는 스토어 출시와 운영이다.

확인할 내용:

- 운동 기록이 저장된다
- 컨디션, 목표 달성, 내일 훈련이 확률과 정해 둔 문장으로 나온다
- 성립한 러너 유형 뱃지가 기록 카드에 나온다
- Jev API 키가 폰에 들어 있지 않다
- 서피스가 절전에 들어가면 서버에 연결되지 않는다는 것이 사용자에게 보인다

## P. 스토어

O를 마친 뒤에 시작한다. 그 전에는 개발자 계정과 앱 패키지 이름을 정하지 않는다.

- Apple 개발자 계정, 인증서, HealthKit 권한
- iPhone 빌드. Xcode가 있는 Mac에서 만든다. 그 Mac은 클라우드 빌드일 수 있다
- Google Play 계정, Android 빌드
- 개인정보 처리방침과 스토어 설명. 웹의 처리방침을 그대로 복사하지 않는다. 계정과 건강 데이터를 다루는 내용을 따로 적는다

## Q. 운영 서버

P 다음에 시작한다. 스토어에 나가는 앱은 집의 서피스 프로를 서버로 쓰지 않는다. 업체는 실제 트래픽과 비용을 확인한 뒤에 정한다. E에서 정한 API 형식은 그대로 둔다.

개발 서버와 다른 것:

- 서버 장비
- Jev API 키
- 운동 기록을 저장하는 위치

운영용 키는 서피스의 개발용 키와 따로 둔다.

## R. 워치

폰 앱과 운영 서버가 된 뒤에 한다. [features/live-pace.md](features/live-pace.md)는 나중 기능이다.

- 애플워치는 SwiftUI, 웨어 OS는 Kotlin. 앱은 둘이다
- 워치에서 Jev를 직접 호출하지 않는다
- 첫 화면을 오늘의 판단으로 할지, 달리는 중 페이스로 할지
- 운동 데이터를 얼마나 자주 받을지
- 심박을 어디에서 받을지
- 화면이 잠겼을 때 무엇을 보여줄지
- 폰과 통신이 끊기면 무엇을 보여줄지

## S. 하지 않는 일

다음 원칙은 처음부터 끝까지 지킨다.

- 웹앱에 새 기능을 넣지 않는다
- 웹앱을 웹뷰로 감싸 스토어에 내지 않는다
- 웹앱을 React로 다시 만들지 않는다
- 티어와 VDOT를 Jev에게 계산시키지 않는다
- Jev에게 사용자에게 보여줄 문장을 쓰게 하지 않는다
- [parked.md](parked.md)의 후보는 만들지 않는다. 캡처 인증, 얼굴 위치 배치, 사진 품질 점수, 테이퍼, 부상 판단, 시즌 배지
- 판단 보류를 Jev의 선택지로 보내지 않는다
- 운동 기록을 사람이 임의로 요약해서 Jev에 넘기지 않는다. Jev에 넘기는 파생 값은 코드에 적어 둔 규칙으로 계산한 것만 쓴다
- 한 판단의 결과를 다른 판단의 입력으로 쓰지 않는다
