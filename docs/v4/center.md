# v4 중심

이 문서는 v4 제품의 중심 정의를 정리하는 초안이다.  
전체 작업 목록은 [index.md](index.md)에 있다.

기능의 입력과 세부 흐름은 각 기능 문서에만 적는다. 이 문서에는 같은 내용을 다시 적지 않는다.

표시는 세 가지로 구분한다.

- **결정** — 대화에서 이미 확정한 내용
- **말한 것** — 방향이나 예시로 언급한 내용. 아직 범위가 확정된 것은 아니다.
- **제안** — 검토를 위해 제시한 내용. 결정하기 전까지는 확정된 것으로 보지 않는다.

아직 결정하지 않은 내용은 비워 둔다. 추측해서 채우지 않는다.

## 결정

웹앱 버전은 `main`의 `9171085`에서 개발을 종료한다.  
그 이후에는 웹앱에 새로운 기능을 추가하지 않는다.

다음 제품은 러닝 앱이다.

이 앱의 핵심 차별점은 러닝 코치가 정한 규칙으로 하는 **의사결정 기능**이다. 규칙은 [rules.md](rules.md)다.

규칙은 미리 정해진 선택지 중 하나와 그 이유를 낸다.  
문장은 우리가 써 둔 템플릿만 쓴다.

그 외의 기능은 앱에서 직접 만든다.

- 판단 결과를 보여 주는 문장
- 사진 편집
- 화면 구성
- 경로를 보여 주는 방식
- 선택지에 표시할 문구
- 코칭 문구
- 내일 훈련 제안 문구

판단 규칙은 다음과 같은 경우에만 사용한다.

- 선택지가 정해진 판단
- 판단 결과에 따라 사용자가 다른 행동을 선택하게 되는 기능
- 기록이 부족할 때 결과를 보류할 수 있는 기능

다음 기능에는 판단 규칙을 사용하지 않는다.

- 건강 앱에서 운동 데이터를 가져오는 기능
- 운동 경로와 기록을 보여 주는 기능
- 사진 편집과 합성
- 티어와 VDOT 계산
- 문장 생성
- 이미 숫자로 명확하게 비교할 수 있는 규칙

hoohaa.run에서 사용하는 VDOT와 티어 계산 기준은 그대로 유지한다.  
숫자 계산과 판단 모두 코드가 한다. 외부 판단 API(TypeSafe Jev)는 쓰지 않으므로 그 API 키도 없다.

판단을 어디서 계산하는지는 [engine.md](engine.md)에 정의한다. 판단 이력이 쌓이면 학습 모델(예: 미세조정한 Laya)을 다시 볼 수 있다.

새 앱의 이름은 **hoohaa**다.  
웹과 앱을 서로 다른 제품 이름으로 나누지 않는다.

웹의 주소는 **hoohaa.run**이다. 계산기와 공유 카드가 있고, 이 웹은 고치지 않는다.

앱은 스토어에서 배포하는 모바일 앱이므로 별도의 웹 주소가 필요하지 않다.

**결정.** 앱은 hoohaa.run 웹을 호출하지 않는다. 계정, 운동 기록, 운동 후 규칙 판단은 별도의 API를 통해 처리한다. 개발 중에는 이 API를 집 서피스 프로에서 운영하며, HTTPS 개발용 주소를 별도로 사용한다. 운영 전환 시 API 서버만 교체하고 앱의 API 호출 형식은 유지한다. 개발용 API 주소의 이름은 아직 정하지 않는다. 문서에서는 `<개발용 API 주소>`로만 적는다.

### 웹과 앱의 관계

새 앱은 hoohaa.run의 **모바일 확장 제품**이다.  
기존 웹앱의 화면과 기능을 모바일로 그대로 옮기는 것은 아니다.

- hoohaa.run은 현재 웹앱 상태로 유지한다.
- 기존 웹 화면을 모바일 앱에서 그대로 복제하지 않는다.
- 새 앱은 러닝 기록을 지속적으로 저장하고 건강 데이터를 받아 판단한다.
- 티어와 VDOT 계산 기준은 웹과 앱에서 동일하게 사용한다.
- 계정과 운동 기록은 하나의 사용자 데이터로 관리한다.
- 웹과 앱이 서로 별도의 기록을 복사해서 보관하지 않는다.
- 현재 웹앱에는 로그인 기능이 없다.
- 이 결정에 따라 기존 웹앱에 로그인을 추가하지 않는다.
- 공유 카드는 기존 웹의 공유 경험과 연결한다.

### 대상 사용자

SNS에 러닝 기록과 사진을 공유하는 젊은 러너를 대상으로 한다.

### 판단에 사용하는 데이터

판단 규칙에 넣는 데이터는 다음 중 하나다.

- 운동 기록 자체
- 코드에 정의된 규칙으로 운동 기록에서 계산한 값

사람이 임의로 요약한 내용은 규칙에 넣지 않는다.

컨디션과 목표는 서로의 판단 결과를 입력으로 사용하지 않는다.  
내일 훈련은 그날의 컨디션 결과를 첫 규칙으로 받는다. [rules.md](rules.md)를 본다.

러너 유형은 기록 카드에 붙는 뱃지다. 코드가 조건을 본다. [features/runner-type.md](features/runner-type.md)

## 결정

### 한 줄 소개

> 러닝 기록을 티어와 예쁜 카드로 남기고, AI가 다음 훈련까지 안내해 줘요.

AI가 소개 문장을 직접 작성하지 않는다.

## 말한 것

사용자가 피트니스 앱 등으로 운동을 끝내면, 그 기록은 건강 앱에 쌓인다. 폰 앱이 그 기록과 경로를 자동으로 읽는다. 사용자가 파일이나 사진을 직접 올리지 않는다.

가져온 기록을 이용해 다음 기능을 제공하는 방향을 이야기했다.

- 기록을 사진으로 편집
- 러닝 코칭
- 내일 훈련 제안

그 외에 추가할 기능은 아직 정해지지 않았다.

검토했지만 현재 범위에 포함하지 않은 후보는 [parked.md](parked.md)에 기록한다.

앱스토어와 Google Play에 모바일 앱을 출시하고, 이후 워치 앱도 만든다.

기능의 정의는 공통으로 유지하고, 기기별로 필요한 화면과 기기 기능만 별도로 구현한다.

구체적인 개발 순서는 [platforms.md](platforms.md)에 따른다.

## 개발할 때

1. [index.md](index.md)를 읽고 현재 작업할 기능의 문서 하나만 연다.
2. 해당 기능 문서에 아직 결정하지 않은 내용이 있으면 그 기능을 구현하지 않는다.
3. 다른 기능의 동작을 변경해야 한다면 해당 기능 문서를 먼저 수정한다. 이 문서에는 필요한 공통 원칙만 추가한다.
4. 여러 기능에 영향을 주는 공통 규칙을 변경해야 한다면 이 문서를 먼저 수정하고, 이후 관련 기능 문서를 수정한다.
